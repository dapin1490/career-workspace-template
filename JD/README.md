# 채용 공고 폴더 관리 가이드

## 1. 공고의 생애 주기

1. **시작**: 공고는 `JD/공고명.md` 단일 파일로 시작합니다. `template.md`를 복사해 프론트매터(단계, 마감일, 회사 유형 등)를 채웁니다. Obsidian을 쓴다면 루트의 `JD 목록.base`로 공고 목록을 표로 봅니다.
2. **승격**: 자소서 초안, 리서치, 면접 준비처럼 작업 파일이 생기면 **같은 이름의 폴더**를 만들고 메인 md를 그 안으로 옮깁니다.
3. **제출**: 제출을 마치면 폴더(또는 파일)를 `JD/Submitted/YYYY-MM/`으로 옮깁니다. 기준은 제출한 달입니다.
    - **제출 대기**: 자기소개서와 지원 양식을 모두 검토하면 메인 문서 프론트매터에 `제출 대기: true`를 켭니다. 검사 스크립트를 쓴다면 이때부터 자동 검사가 증빙을 요구합니다(`scripts/README.md`).
    - 옮기기 전에 `submitted/`에 **제출 완료 증빙**(지원 완료 화면이나 접수 확인 이메일 캡처, 파일 이름에 `제출 완료 증빙` 포함)이 있어야 합니다. 저장본이나 미리보기 PDF는 증빙이 아닙니다. 증빙이 없으면 `단계`를 `지원 완료`로 바꾸지 않습니다(`AGENTS.md` 행동 규칙 8번).
    - 증빙을 확인하면 `제출 대기`를 지우고 `단계`를 `지원 완료`로 바꾼 뒤 옮깁니다. 이렇게 해야 검사 대상이 쌓이지 않습니다.
4. **폐기**: 기간 만료, 지원 불가, 부적절 판정이면 `JD/DEPRECATED/`로 옮깁니다. 에이전트는 이 폴더를 참고하지 않습니다.

### 1-1. 마감일 표기 (권장 관례, 원하지 않으면 이 절을 지우십시오)

- 프론트매터 `마감일`은 실제 마감이 자정(23:59)이면 그 날짜를 그대로 적습니다.
- 자정이 아닌 시각(예: 11시, 18시)이면 **전날로 당겨** 적습니다. 애매한 시각을 놓치지 않고 여유를 두기 위한 의도적 표기입니다.
- 그래서 프론트매터 날짜와 본문의 실제 마감 일정이 다를 수 있습니다. 에이전트는 이 차이를 오류로 지적하거나 수정을 제안하지 않습니다. 실제 마감 시각이 필요하면 본문이나 사용자에게 확인합니다.

## 2. 폴더 표준 구조 (승격한 뒤)

```
회사_직무/
├── 회사_직무.md      ← 메인 문서: 프론트매터 + 공고 요약 + 지원 양식 답안 + 제출 서류 리스크 메모
├── README.md         ← (파일이 많아지면) 폴더 인덱스
├── jd/               ← 공고 원문, 모집요강 PDF, 회사 공지와 안내 메일
├── submitted/        ← 실제로 제출한 것만. 제출 후 수정 금지
├── interview/        ← 면접 준비 노트, 후기, 일정 안내
├── Artifacts/        ← 에이전트 산출물(초안, 리서치, 검토 피드백)
└── ref/              ← 외부 참고자료(기사, 블로그 사본, 첨부 이미지)
```

| 위치 | 작성 주체 | 수정 |
|---|---|---|
| 메인 md | 사람 | 상시 |
| `jd/` | 사람(수집) | 원문이므로 수정하지 않음 |
| `submitted/` | 사람(제출 시 복사) | **제출 후 수정 금지** |
| `interview/` | 사람. AI가 쓴 내용은 `history/README.md` 6절의 라벨을 붙임 | 상시 |
| `Artifacts/` | 에이전트 | 상시 |
| `ref/` | 사람(수집) | 수정하지 않음 |

- 하위 폴더는 필요할 때만 만듭니다. 빈 폴더를 미리 만들 필요는 없습니다.

## 3. 최종본 규칙

- **같은 문서의 버전을 파일로 여러 개 남기지 않습니다.** "노트"와 "노트 최종본", "피드백 (1)"과 "피드백 (2)"를 함께 두지 말고, 덮어쓴 뒤 커밋합니다. 버전 관리는 git이 합니다.
- 이전 버전을 꼭 남겨야 하면 `Artifacts/archive/`로 옮깁니다.
- **실제로 낸 서류는 `submitted/`에만 둡니다.** 제출하는 순간 자소서 문항과 답안 원문, 이력서와 포트폴리오 PDF를 복사해 두고 이후에는 고치지 않습니다. 면접 전에 "내가 실제로 무엇을 주장했는가"를 확인하는 유일한 근거입니다.

## 4. 제출 서류 리스크 메모

- 메인 md 끝에 `# 제출 서류 리스크 메모 (면접 대비)` 섹션을 둡니다.
- 제출본의 표현 중 이력 원본과 어긋나거나 과장된 것을 기록하고, 면접에서 질문받으면 어떻게 답할지 적습니다.
    - 예: 실제로 다루지 못하는 기술이 기술 스택에 적혀 있음
    - 예: 수상 사유를 단정한 문장
- 이력 원본을 정정했을 때 이 섹션을 채우는 절차는 `history/README.md` 7절(정정 체크리스트)을 따릅니다.
